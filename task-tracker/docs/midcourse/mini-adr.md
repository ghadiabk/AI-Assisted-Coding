# Mini Architectural Decision Record (ADR)

## Context & Problem Statement
To complete the Mid-Course Project, the Task Tracker application requires two additional capabilities:
1. Categorization via task tags/labels.
2. Board filtering via keyword search and combined parameter queries.

The primary constraint is maintaining the simple, testable, in-memory architecture established in Modules 1–3 without adding unnecessary external dependencies or infrastructure.

## Selected Solutions & Architecture

### 1. Tag Storage and Validation
* **Model Layer:** Tags are defined as an `Optional[List[str]]` in Pydantic models (`TaskCreate`, `TaskUpdate`, and `TaskResponse`).
* **Validation:** Sanitization (whitespace stripping) and constraint checks (maximum 5 tags, maximum 20 characters per tag) are implemented in `app/models/task.py` using Pydantic v2 `@field_validator("tags", mode="before")`.
* **Storage Layer:** Tags are stored as a standard Python `list` inside each task dictionary in `app/storage/tasks.py` and persisted to `tasks.json`.

### 2. Multi-Parameter Filtering Endpoint
* **Backend:** The `GET /tasks` endpoint in `app/main.py` was expanded to accept `search` and `tag` as optional `Query` parameters alongside `status` and `priority`.
* **Execution:** Filtering is evaluated sequentially on the in-memory array retrieved via `get_all_tasks()`. Substring and tag matches are evaluated case-insensitively using Python standard library string methods.
* **Frontend Integration:** The UI fetches tasks using dynamic URL parameters generated by `URLSearchParams`. Inputs on the frontend filter bar trigger network calls throttled by a 300ms JavaScript `debounce` wrapper.

## Alternatives Suggested by AI and Rejected

1. **Relational Database Schema for Tags:**
   * *AI Proposal:* The AI suggested migrating to SQLite using SQLModel/SQLAlchemy with a dedicated `Tag` table and a `task_tags` junction table.
   * *Reason for Rejection:* Rejected to prevent scope creep. Relational overhead adds migrations and complex connection handling that obscure the core AI-assisted workflow focus.

2. **Frontend-Side Only Filtering:**
   * *AI Proposal:* The AI suggested loading all tasks once on startup and filtering the `localTasks` array locally in JavaScript.
   * *Reason for Rejection:* Rejected because it violates the principle of keeping the backend API as the single source of truth for query logic.

3. **External Full-Text Search Libraries:**
   * *AI Proposal:* The AI suggested adding `whoosh` or configuring ElasticSearch for text querying.
   * *Reason for Rejection:* Native string operations are sufficient for in-memory dictionaries and avoid adding third-party dependencies.
